# Правила оформления коммитов

В проекте используется формат Conventional Commits. Он помогает читать историю,
находить изменения по компонентам и в дальнейшем автоматически собирать changelog.

## Формат

```text
<type>(<scope>): <description>

[необязательное пояснение]

[необязательные ссылки на задачи и описание несовместимости]
```

`type` и `description` обязательны. `scope` указывается, когда изменение относится
к конкретному компоненту; для общего изменения его можно опустить.

## Типы изменений

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новая возможность системы |
| `fix` | Исправление ошибки |
| `docs` | Изменение документации |
| `refactor` | Изменение структуры кода без новой функциональности и исправления ошибок |
| `perf` | Улучшение производительности |
| `test` | Добавление или изменение тестов |
| `build` | Изменение сборки, зависимостей или упаковки |
| `ci` | Изменение автоматических проверок и CI/CD |
| `style` | Форматирование кода без изменения поведения |
| `chore` | Обслуживание репозитория, не попадающее в другие категории |
| `revert` | Отмена предыдущего коммита |

Визуальные изменения веб-интерфейса относятся к `feat` или `fix`, а не к `style`.

## Области изменений

Используйте короткие названия в нижнем регистре:

| Scope | Компонент |
| --- | --- |
| `gateway` | API gateway |
| `orchestrator` | Управление вычислительным пайплайном |
| `processing` | Обработка данных |
| `aggregation` | Агрегирование результатов |
| `plugins` | Плагинный механизм и методы агрегирования |
| `web` | Демонстрационный веб-клиент |
| `contracts` | Общие интерфейсы, контракты и схемы |
| `observability` | Мониторинг, метрики и логирование |
| `deploy` | Контейнеры и развёртывание |
| `deps` | Зависимости |
| `repo` | Настройки и структура репозитория |

Список можно расширять по мере появления компонентов. Не перечисляйте несколько
scope через запятую: выберите основную область или опустите scope.

## Правила заголовка

- Пишите заголовки на английском языке для единой истории проекта.
- Используйте повелительную форму: `add`, `fix`, `remove`, `update`.
- Начинайте описание со строчной буквы и не ставьте точку в конце.
- Стремитесь уложить весь заголовок в 72 символа.
- Описывайте конкретное изменение: избегайте `update code`, `fix bugs`, `changes`, `wip`.
- Один коммит должен содержать одно логически завершённое изменение.
- Не смешивайте независимый рефакторинг, новую функцию и исправление ошибки.
- Не добавляйте в заголовок дату, имя автора или хеш: Git уже хранит эти данные.

## Тело коммита и ссылки на задачи

Отделяйте тело от заголовка пустой строкой. Для нетривиальных изменений объясняйте
причину, прежнее поведение и важные ограничения. Не пересказывайте построчно diff.
Тело можно писать на русском или английском языке.

В конце при необходимости укажите `Refs: #42` для связи с задачей или
`Closes #42`, если изменение полностью решает задачу. Номер задачи необязателен.

```text
fix(orchestrator): prevent duplicate task execution

Повторная доставка сообщения приводила к повторному запуску вычисления.
Проверка идентификатора задачи позволяет вернуть уже сохранённый результат.

Closes #42
```

## Несовместимые изменения

Если изменение требует действий от потребителей API, плагинов или конфигурации,
поставьте `!` перед двоеточием. В footer `BREAKING CHANGE:` опишите, что изменилось
и как перейти на новый вариант. Это правило действует для любого типа коммита.

```text
feat(contracts)!: require a version in aggregation requests

BREAKING CHANGE: поле version стало обязательным. Добавьте version: 1
во все запросы агрегирования перед обновлением сервиса.
```

## Примеры для проекта

```text
chore(repo): add initial project directories
chore(repo): ignore local development artifacts
docs: define commit message conventions
feat(plugins): add aggregator registration
feat(orchestrator): execute independent pipeline stages concurrently
fix(aggregation): handle empty ranking input
perf(processing): limit worker pool allocations
test(plugins): cover duplicate aggregator registration
build(deps): update Go dependencies
ci: run Go tests on pull requests
docs(contracts): describe aggregation request schema
```

Для отмены изменения используйте заголовок `revert: <исходный заголовок>`
и укажите в теле хеш отменяемого коммита и причину отката.

## Перед коммитом

Проверьте staged diff, отсутствие секретов и случайных файлов. Выполните проверки,
относящиеся к изменению: например, форматирование Go-кода и тесты затронутых пакетов.
Убедитесь, что заголовок описывает именно содержимое коммита.

При squash merge оформляйте итоговый коммит по тем же правилам. Если платформа
берёт его заголовок из PR, используйте этот формат и для названия PR.

Эти правила пока проверяются вручную; автоматическая проверка не настроена.
